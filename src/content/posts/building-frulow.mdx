# Frulow / LibQuest: Enterprise Monorepo Architecture and the DX Payoff

The initial architecture for Frulow utilized decoupled repositories: `LibQuest` (frontend) and `libquest-be` (backend). While decoupled repositories often promise reduced surface area and strong boundary enforcement, they can introduce severe friction when API contracts evolve rapidly. 

To address mounting integration overhead, the architecture was migrated to a unified `monorepo-libquest`. This document outlines the technical rationale, the implementation strategy, and the measurable return on investment (ROI) in developer experience and system stability.

---

## The Distributed Type Drift Problem

Prior to the migration, the multi-repository architecture introduced three critical failure modes:

1. **Type Definition Drift**: Core domain entities (`UserDTO`, `QuestPayload`, `PaginatedResponse<T>`) were duplicated across repositories. A schema modification in the backend resulted in runtime failures on the frontend, rather than compile-time errors.
2. **Validation Logic Divergence**: Zod schemas were utilized for request validation on the backend and form validation on the frontend. Without a shared source of truth, these inevitably diverged (e.g., the server demanding ISO 8601 strings while the client submitted Date objects). These regressions were typically caught during integration testing rather than CI.
3. **Utility Function Duplication**: Common business logic—date formatting, string sanitization, and pagination algorithms—were copied across repositories, leading to inconsistent application of bug fixes.

The fundamental architectural issue: **sharing code securely between decoupled TypeScript repositories mandates a rigid package publication pipeline.** While private NPM registries are appropriate for stable, versioned libraries, they introduce unacceptable latency for rapidly evolving internal API contracts.

---

## The Monorepo Implementation Strategy

A Workspace-based monorepo (utilizing Yarn Workspaces and Turborepo) was selected to provide the minimum viable abstraction layer for code sharing without the overhead of heavy micro-frontend orchestrators.

The architecture was restructured as follows:

```text
monorepo-libquest/
├── packages/
│   ├── types/          # Shared TypeScript interfaces, Zod validation schemas
│   │   └── src/
│   │       ├── entities.ts
│   │       ├── api.ts      # Strict request/response DTOs
│   │       └── validation.ts
│   └── client/         # Strongly typed HTTP client for frontend consumption
│       └── src/
│           └── index.ts
├── apps/
│   ├── LibQuest/       # Next.js frontend application
│   └── libquest-be/    # Fastify backend service
└── package.json        # Workspace root configuration
```

```json
// package.json (root)
{
  "workspaces": ["packages/*", "apps/*"],
  "scripts": {
    "dev": "turbo dev",
    "type-check": "tsc --build"
  }
}
```

```json
// apps/LibQuest/package.json
{
  "dependencies": {
    "@libquest/types": "*",   // Resolved via local symlink — no publish pipeline required
    "@libquest/client": "*"
  }
}
```

By leveraging workspace symlinking, modifications in `packages/types/src/entities.ts` propagate instantly to all consumer applications, eliminating publication pipelines, version bumping, and reinstallation cycles.

## The Shared Type Layer: Enforcing the API Contract

The `@libquest/types` package serves as the immutable contract between the client interface and the server execution environment:

```ts
// packages/types/src/entities.ts
export interface Quest {
  id: string;
  title: string;
  description: string | null;
  status: QuestStatus;
  createdAt: string; // Enforced ISO 8601 serialization across the network boundary
  updatedAt: string;
}

export type QuestStatus = "active" | "completed" | "archived";
```

```ts
// packages/types/src/api.ts
import type { Quest } from "./entities";

// Request Data Transfer Objects (DTOs)
export interface CreateQuestRequest {
  title: string;
  description?: string;
}

// Standardized Paginated Responses
export interface PaginatedResponse<T> {
  data: T[];
  total: number;
  page: number;
  pageSize: number;
}

export type GetQuestsResponse = PaginatedResponse<Quest>;
```

```ts
// packages/types/src/validation.ts — Shared Zod schemas
import { z } from "zod";

export const createQuestSchema = z.object({
  title: z.string().min(3).max(120).trim(),
  description: z.string().max(2000).optional(),
});
```

This ensures absolute parity. When business requirements necessitate altering a field constraint (e.g., modifying a maximum character limit), a single file modification instantly surfaces TypeScript compiler errors across all dependent modules violating the new contract.

## The Strongly Typed API Client

To further insulate the frontend from network implementation details, the `@libquest/client` package encapsulates native HTTP calls with strict type signatures:

```ts
// packages/client/src/index.ts
import type { CreateQuestRequest, GetQuestsResponse, Quest } from "@libquest/types";

export class LibQuestClient {
  constructor(private baseUrl: string, private getToken: () => string | null) {}

  private async request<T>(path: string, init?: RequestInit): Promise<T> {
    const token = this.getToken();
    const res = await fetch(`${this.baseUrl}${path}`, {
      ...init,
      headers: {
        "Content-Type": "application/json",
        ...(token ? { Authorization: `Bearer ${token}` } : {}),
        ...init?.headers,
      },
    });
    
    if (!res.ok) {
      const error = await res.json().catch(() => ({ message: "Unknown API error" }));
      throw new ApiError(res.status, error.message);
    }
    
    return res.json() as T;
  }

  async getQuests(page = 1): Promise<GetQuestsResponse> {
    return this.request(`/v1/quests?page=${page}`);
  }

  async createQuest(payload: CreateQuestRequest): Promise<Quest> {
    return this.request("/v1/quests", {
      method: "POST",
      body: JSON.stringify(payload),
    });
  }
}
```

The frontend application never interacts directly with raw `fetch` APIs. When backend engineers modify an endpoint signature, the TypeScript compiler immediately catches the discrepancy in the client SDK before CI validation begins.

## Zero-Downtime Database Migrations

Operating a unified codebase requires rigorous database migration strategies. **Deploying schema alterations and application logic simultaneously is unsafe and breaks rollback capabilities.**

The platform implements the Expand/Contract (Parallel Change) deployment pattern:

```text
Step 1: Expand Phase (Backward-compatible schema alteration)
  - Add column as NULLABLE: ALTER TABLE quests ADD COLUMN priority VARCHAR;

Step 2: Application Deployment
  - Deploy new application code designed to handle both NULL and populated states gracefully.

Step 3: Data Backfill
  - Execute background workers: UPDATE quests SET priority = 'normal' WHERE priority IS NULL;

Step 4: Constraint Enforcement
  - ALTER TABLE quests ALTER COLUMN priority SET NOT NULL;

Step 5: Contract Phase
  - Remove deprecated code paths handling the legacy NULL state.
```

While this introduces multiple deployment phases, it guarantees that every individual step is independently and safely rollbackable, a requirement for high-availability production environments.

## Architectural ROI

Implementing a strict monorepo architecture yields significant returns in operational stability and development velocity:

- **Elimination of Type Drift**: Zero instances of runtime type mismatches between client and server environments.
- **Unified Pull Requests**: A single pull request encompasses both the API contract modification and its frontend implementation, providing reviewers with full contextual visibility.
- **Streamlined Onboarding**: Engineers can trace the entire execution flow—from database schema to UI component—within a single, coherent workspace.

The true value of this architecture is operational confidence. When refactoring complex flows like authentication or pagination, the TypeScript compiler acts as an automated integration test, surfacing required updates deterministically before they reach runtime execution.
