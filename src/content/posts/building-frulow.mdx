# Frulow / LibQuest: Monorepo Architecture and the DX Payoff

I started Frulow with two separate repos: `LibQuest` (frontend) and `libquest-be` (backend). It seemed like the right move — small surface area, easy to reason about, fast to get running.

Twelve weeks in, I migrated to `monorepo-libquest`. Here's the honest account of why, how, and what it cost vs. what it earned.

---

## The problem that forced the monorepo

By week 8, I had three types of duplication:

1. **Type definitions**: `UserDTO`, `QuestPayload`, `PaginatedResponse<T>` existed in both repos. When I changed a field name in the backend, the frontend would break at runtime — not at compile time, because they were separate TypeScript projects.

2. **Validation logic**: I had Zod schemas for request validation on the server and client-side form validation on the frontend. They diverged. The server accepted `date_of_birth` as an ISO string; the frontend sent `birthDate` as a Date object. I caught this in QA, not in CI.

3. **Utility functions**: Date formatting, string sanitization, pagination helpers — copied between repos. When I fixed a bug in the backend copy, the frontend had the old version.

The core issue: **sharing code between two separate TypeScript projects requires a package publish step**. There's no native way to `import { UserDTO } from "../../../backend/src/types"` across repos. You have to publish to npm (or a private registry), version it, and update the consumer. That's fine for a mature product. It's friction death for a solo project.

---

## The monorepo solution

I chose a Yarn workspaces monorepo — not a Turborepo, not an Nx setup. Here's why: I wanted the minimum abstraction layer that solved my problem. Turborepo adds caching and pipeline orchestration. That's great at 10+ packages. At 3 packages, it's configuration overhead.

The final structure:

```
monorepo-libquest/
├── packages/
│   ├── types/          # Shared TypeScript interfaces, Zod schemas
│   │   └── src/
│   │       ├── entities.ts
│   │       ├── api.ts      # request/response shapes
│   │       └── validation.ts
│   └── client/         # Typed API client for frontend
│       └── src/
│           └── index.ts
├── apps/
│   ├── LibQuest/       # Next.js frontend
│   └── libquest-be/    # Fastify backend
└── package.json        # workspace root
```

```json
// package.json (root)
{
  "workspaces": ["packages/*", "apps/*"],
  "scripts": {
    "dev": "turbo dev",
    "type-check": "tsc --build"
  }
}
```

```json
// apps/LibQuest/package.json
{
  "dependencies": {
    "@libquest/types": "*",   // resolved locally — no publish step
    "@libquest/client": "*"
  }
}
```

The `"*"` version means "resolve from workspace" — Yarn symlinks the local package directly. Changes in `packages/types/src/entities.ts` are instantly visible in both apps, with no publish, no version bump, no reinstall.

## The shared type layer — what it actually contains

The `@libquest/types` package is not just interfaces. It's the contract between client and server:

```ts
// packages/types/src/entities.ts
export interface Quest {
  id: string;
  title: string;
  description: string | null;
  status: QuestStatus;
  createdAt: string; // ISO 8601 — always string across the wire
  updatedAt: string;
}

export type QuestStatus = "active" | "completed" | "archived";
```

```ts
// packages/types/src/api.ts
import type { Quest } from "./entities";

// Request shapes
export interface CreateQuestRequest {
  title: string;
  description?: string;
}

// Response shapes with pagination
export interface PaginatedResponse<T> {
  data: T[];
  total: number;
  page: number;
  pageSize: number;
}

export type GetQuestsResponse = PaginatedResponse<Quest>;
```

```ts
// packages/types/src/validation.ts — Zod schemas (used on both sides)
import { z } from "zod";

export const createQuestSchema = z.object({
  title: z.string().min(3).max(120).trim(),
  description: z.string().max(2000).optional(),
});
```

The backend uses `createQuestSchema` for request validation. The frontend uses the same schema for form validation. One change — one place. When a product requirement changes the max title length from 120 to 80, I change one file and TypeScript errors immediately surface everywhere that violates the new constraint.

## The typed API client

The `@libquest/client` package wraps fetch with types:

```ts
// packages/client/src/index.ts
import type { CreateQuestRequest, GetQuestsResponse, Quest } from "@libquest/types";

export class LibQuestClient {
  constructor(private baseUrl: string, private getToken: () => string | null) {}

  private async request<T>(path: string, init?: RequestInit): Promise<T> {
    const token = this.getToken();
    const res = await fetch(`${this.baseUrl}${path}`, {
      ...init,
      headers: {
        "Content-Type": "application/json",
        ...(token ? { Authorization: `Bearer ${token}` } : {}),
        ...init?.headers,
      },
    });
    
    if (!res.ok) {
      const error = await res.json().catch(() => ({ message: "Unknown error" }));
      throw new ApiError(res.status, error.message);
    }
    
    return res.json() as T;
  }

  async getQuests(page = 1): Promise<GetQuestsResponse> {
    return this.request(`/v1/quests?page=${page}`);
  }

  async createQuest(payload: CreateQuestRequest): Promise<Quest> {
    return this.request("/v1/quests", {
      method: "POST",
      body: JSON.stringify(payload),
    });
  }
}
```

The frontend never calls `fetch` directly. It goes through this typed client. When the backend changes an endpoint signature, TypeScript catches the mismatch in the client package before CI runs.

## Zero-downtime database migrations

One pattern I learned the hard way: **you cannot deploy schema changes and application changes simultaneously in a way that's safe for rollback**.

The wrong way:

```sql
-- Migration
ALTER TABLE quests ADD COLUMN priority VARCHAR NOT NULL DEFAULT 'normal';

-- Same deployment
SELECT id, title, priority FROM quests WHERE ...
```

If the deployment fails after the migration runs, rolling back the application still needs the `priority` column to exist. Now you can't rollback the migration without breaking the old code.

The right way — expand/contract pattern:

```
Step 1: Expand (backward-compatible migration)
  - Add column as NULLABLE: ALTER TABLE quests ADD COLUMN priority VARCHAR;

Step 2: Deploy new code
  - Code handles both NULL and set priority gracefully.

Step 3: Backfill
  - UPDATE quests SET priority = 'normal' WHERE priority IS NULL;

Step 4: Enforce constraint
  - ALTER TABLE quests ALTER COLUMN priority SET NOT NULL;

Step 5: Contract (remove old code paths)
```

It's more steps. But every step is independently rollbackable.

## What the monorepo actually cost

**Setup time**: ~2 days. Migrating types, setting up workspace symlinks, updating import paths, fixing TypeScript project references.

**Tooling friction**: You need to understand how `yarn workspaces run` works, how TypeScript path mappings interact with `tsconfig.json` `references`, and why your IDE sometimes doesn't pick up workspace changes without restarting the TS language server.

**Build complexity**: Building in the right order matters. `types` must compile before `client`, which must compile before `apps`. This is trivial with `tsc --build` (project references), but it's a mental model you have to adopt.

---

## What it earned

- Zero type drift between client and server since the migration. Zero.
- One PR changes both the API contract and the frontend consumer. Reviewers see the full change.
- New engineers (even hypothetically) understand the API contract by looking at one package — not reading Swagger docs that may or may not be current.

The real payoff is confidence. When I refactor the auth flow or change how pagination works, TypeScript tells me every place I need to update. I don't discover the drift at runtime.

---

## When to reach for a monorepo

Don't start with a monorepo. Start with the simplest thing. Add a monorepo when:

1. You have real code that legitimately needs to be shared between multiple apps (not just copy-pasted utilities).
2. Type drift between your client and server is causing bugs that TypeScript should be catching.
3. The overhead of a separate publish step is slowing down development cycles.

That's exactly where I was. The monorepo was the answer to a specific, concrete problem — not a setup choice made upfront because it seemed sophisticated.
