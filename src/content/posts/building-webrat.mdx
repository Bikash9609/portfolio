# Building Webrat: Decentralized Trust as a Chrome Extension

The modern web's trust problem is not strictly a malware problem — it is fundamentally a *human behavior* problem. Traditional security tools excel at catching binary threats and known malicious signatures. They fail to identify highly obfuscated dropshipping operations or predatory e-commerce policies.

**Webrat** was engineered to solve this through community-driven safety ratings that surface human-assessed risk signals. Building an extension to handle this involves strict technical constraints: the software runs in real-time alongside every web page, must guarantee strict data privacy, maintain a near-zero latency footprint, and securely handle authenticated data.

---

## The Extension Architecture: Event-Driven and Privacy-First

Chrome extensions operate under a specific execution model that dictates architectural boundaries:

- **Service Worker** (Background): Handles extension lifecycle, message routing, and browser events. Operates outside the DOM.
- **Content Script**: Injected directly into pages. Has DOM access but executes within a sandboxed context.
- **Popup**: The user interface. A separate document with no shared state to the content scripts outside of explicit message passing.

Naive extension implementations frequently suffer from performance degradation by indiscriminately monitoring tab history or executing redundant backend requests on every page load. Webrat adopts a highly optimized, privacy-first approach:

```ts
// background/service-worker.ts
chrome.tabs.onActivated.addListener(async ({ tabId }) => {
  const tab = await chrome.tabs.get(tabId);
  if (!tab.url || !isHttpUrl(tab.url)) return;
  
  const hostname = new URL(tab.url).hostname;
  
  // Conditionally fetch only upon active tab + hostname change
  const cachedRating = await getRatingFromCache(hostname);
  if (cachedRating) {
    chrome.action.setBadgeText({ text: String(cachedRating.stars), tabId });
    return;
  }
  
  // Non-blocking asynchronous fetch
  fetchAndCacheRating(hostname, tabId);
});
```

Key engineering decisions:
1. **Strict Active-Tab Scoping**: The system evaluates only the active tab's hostname. There is zero batch processing or passive tracking of browsing history.
2. **Cache-First Strategy**: If a domain has been evaluated within the active session, it is served instantly from local memory.
3. **Non-Blocking Execution**: Tab activation is never blocked. The UI badge updates asynchronously when the rating payload arrives (typically <100ms).

## UI Performance: Leveraging React 19

React 19 was selected specifically for its concurrency primitives, which are critical for maintaining a highly responsive extension popup environment:

### Actions and `useTransition`

Extension popups are computationally constrained environments where perceived latency is highly visible. React 19's Actions, combined with `useTransition`, allow the UI to remain interactive during asynchronous network operations without jank or layout shift:

```tsx
// Modern React 19 Action implementation
const [isPending, startTransition] = useTransition();
const handleSubmitRating = (stars: number) => {
  startTransition(async () => {
    await submitRating({ hostname, stars });
    await refreshRatings(hostname);
    // React batches the UI updates, preventing intermediate loading state flicker
  });
};
```

By marking the network update as non-urgent, the current UI remains stable while the rating submission is in flight. In a highly constrained vertical layout, preventing layout shifts from loading spinners significantly improves the user experience.

## Authentication: Navigating the Extension Sandbox

Implementing robust OAuth within a Chrome extension requires navigating complex constraints: there is no persistent URL, no standard server-rendered session context, and popup dimensions are too restrictive for standard login flows.

The canonical Manifest V3 approach utilizing `chrome.identity.launchWebAuthFlow` provides the most secure and reliable implementation:

```ts
// background/auth.ts
export async function initiateGoogleOAuth(): Promise<string> {
  const clientId = process.env.GOOGLE_CLIENT_ID;
  const redirectUri = chrome.identity.getRedirectURL("oauth2");
  
  const authUrl = new URL("https://accounts.google.com/o/oauth2/auth");
  authUrl.searchParams.set("client_id", clientId);
  authUrl.searchParams.set("redirect_uri", redirectUri);
  authUrl.searchParams.set("response_type", "token");
  authUrl.searchParams.set("scope", "openid email profile");
  
  const responseUrl = await chrome.identity.launchWebAuthFlow({
    url: authUrl.toString(),
    interactive: true,
  });
  
  // Extract access token securely from the redirect URL hash
  const hash = new URL(responseUrl).hash;
  const params = new URLSearchParams(hash.substring(1));
  return params.get("access_token")!;
}
```

Offloading authentication to Google OAuth removes the liability of managing passwords, handling account recovery, and securing password hashes. It centralizes trust to a verified provider, ensuring high security with minimal friction.

## Data Layer: Type-Safe SQL with Drizzle ORM

On the backend, Drizzle ORM provides a highly performant, type-safe data access layer. Unlike heavily abstracted ORMs, Drizzle maintains a close mapping to raw SQL, which is crucial for predictable query performance:

```ts
// schema.ts — Drizzle
export const ratings = pgTable("ratings", {
  id: uuid("id").primaryKey().defaultRandom(),
  hostname: varchar("hostname", { length: 255 }).notNull(),
  userId: uuid("user_id").notNull().references(() => users.id),
  stars: integer("stars").notNull(),
  review: text("review"),
  createdAt: timestamp("created_at").defaultNow(),
});

// Explicit, predictable query generation
const avg = await db
  .select({
    hostname: ratings.hostname,
    avgStars: sql<number>`avg(${ratings.stars})::numeric(3,1)`,
    count: count(),
  })
  .from(ratings)
  .where(eq(ratings.hostname, targetHostname))
  .groupBy(ratings.hostname);
```

The explicit casting (`::numeric(3,1)`) ensures exact precision control directly at the database level. Drizzle provides the safety of end-to-end TypeScript types while allowing precise optimization of the underlying SQL execution plans.

## Trust and Security: Preventing System Manipulation

The defining challenge of a community rating platform is preventing coordinated manipulation (review bombing). The architecture addresses this through multiple overlapping security layers:

1. **Strictly Authenticated Writes**: Anonymous submissions are rejected at the API gateway. Every review requires a verified Google OAuth token.
2. **Distributed Rate Limiting**: The system enforces a strict one-rating-per-domain-per-user limit, backed by a high-performance Redis cache:

```ts
async function rateLimitByUser(userId: string, hostname: string): Promise<boolean> {
  const key = `rate:${userId}:${hostname}`;
  const existing = await redis.get(key);
  if (existing) return false; // Request blocked: limit exceeded
  
  await redis.setex(key, 60 * 60 * 24 * 30, "1"); // 30-day TTL enforcement
  return true;
}
```

3. **Reputation Weighting**: The system actively monitors rating patterns, programmatically applying weight penalties to accounts demonstrating statistically anomalous behavior (e.g., exclusively submitting 1-star or 5-star ratings across unrelated domains).

## UI Engineering with Tailwind v4

Webrat utilizes Tailwind v4 for highly efficient styling. The notable architectural shift in v4 is the elimination of `tailwind.config.js` in favor of native CSS variables:

```css
/* globals.css */
@import "tailwindcss";

@theme {
  --color-brand: oklch(65% 0.22 280);
  --font-sans: "Inter", sans-serif;
  --radius: 8px;
}
```

The transition to the browser-native `oklch()` color space guarantees perceptually uniform color scaling. This is particularly vital in an extension UI where color directly communicates critical trust signals (e.g., green for verified safe, red for high risk).

## Architectural Takeaways for the Extension Ecosystem

**Embrace Message Passing**: Extension components are isolated for security. Attempting to bypass `chrome.runtime.sendMessage` leads to unstable memory leaks. Explicit message routing is the only viable pattern for robust extension state management.

**Aggressive Service Worker Caching**: Extension popups are highly ephemeral. Data must be cached in the service worker's memory using a stale-while-revalidate pattern to achieve instant UI responsiveness.

**Design for Ephemerality**: Manifest V3 service workers are aggressively terminated by the browser to preserve system resources. State must never be assumed persistent in memory; it must be backed by `chrome.storage.session` or `chrome.storage.local`.

The resulting architecture delivers an extension that initializes in under 100ms, provides instant cached evaluations, and updates asynchronously without degrading the user's browsing experience. [**Webrat is available online.**](https://webrat.online/)
