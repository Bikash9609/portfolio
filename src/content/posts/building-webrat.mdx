# Building Webrat: Decentralized Trust as a Chrome Extension

The web's trust problem is not a malware problem — it's a *human behavior* problem. Traditional antivirus tools catch binary threats. They don't catch a Shopify store with a 3-month shipping policy buried in the footer, or a dropship operation reselling AliExpress products at 10x markup with no return policy.

That's what Webrat solves: community-driven safety ratings that surface *human-assessed* risk signals, not signature-based malware detection.

The technical constraints are interesting: you're building a real-time companion that runs on every page, can't spy on browsing history, must feel instant, and needs to earn user trust to collect data in the first place.

---

## The extension architecture: event-driven, privacy-first

Chrome extensions have a specific execution model that most developers misunderstand:

- **Service Worker** (background): Handles extension lifecycle, message routing, browser events. Has no access to DOM.
- **Content Script**: Injected into pages. Has DOM access but a sandboxed JS context — can't import npm packages.
- **Popup**: The UI. A completely separate document; no shared state with content scripts without message passing.

Most naive extension implementations either: (a) spy on every URL change to collect history, or (b) make a backend request on every page load.

My approach:

```ts
// background/service-worker.ts
chrome.tabs.onActivated.addListener(async ({ tabId }) => {
  const tab = await chrome.tabs.get(tabId);
  if (!tab.url || !isHttpUrl(tab.url)) return;
  
  const hostname = new URL(tab.url).hostname;
  
  // Only fetch when tab becomes active AND hostname changed
  const cachedRating = await getRatingFromCache(hostname);
  if (cachedRating) {
    chrome.action.setBadgeText({ text: String(cachedRating.stars), tabId });
    return;
  }
  
  // Async fetch — never blocks tab activation
  fetchAndCacheRating(hostname, tabId);
});
```

Key decisions here:
1. **Only the active tab's hostname** — no history collection, no passive tracking
2. **Cache-first**: If we've already rated this domain in this session, serve from cache instantly
3. **Non-blocking fetch**: The tab activates immediately; the badge updates when the rating arrives (~100ms)

This is why the privacy claim holds. We never batch-process your tab history. We only process what you're actively looking at, when you look at it.

## React 19 in an extension popup: what's different

I chose React 19 intentionally — not to stay current, but for specific features:

### Actions and `useTransition`

Extension popups are tiny documents. They should feel snappy. React 19's Actions with `useTransition` let me keep the UI responsive during async operations:

```tsx
// Before (React 18 pattern)
const [loading, setLoading] = useState(false);
const handleSubmitRating = async (stars: number) => {
  setLoading(true);
  try {
    await submitRating({ hostname, stars });
    await refreshRatings(hostname);
  } finally {
    setLoading(false);
  }
};

// After (React 19 Action)
const [isPending, startTransition] = useTransition();
const handleSubmitRating = (stars: number) => {
  startTransition(async () => {
    await submitRating({ hostname, stars });
    await refreshRatings(hostname);
    // React batches the UI updates — no intermediate loading state flicker
  });
};
```

The difference: `useTransition` marks the update as non-urgent. The current UI remains interactive while the rating submission is in flight. In a popup with limited vertical space, preventing layout shifts from loading spinners matters.

## Authentication inside an extension: the UX minefield

Adding Google OAuth to an extension is tricky. You have no persistent URL, no server-rendered session, and popup dimensions that don't accommodate a login flow.

Options I evaluated:

| Approach | Problem |
|----------|---------|
| `chrome.identity.launchWebAuthFlow` | Pops a dedicated browser window. Good UX, but looks unfamiliar. |
| Redirect to extension popup | Popup closes after redirect. Auth state lost. |
| Background service worker auth | Can't open windows from service worker in Manifest V3. |
| Backend-initiated OAuth with `state` param | Requires backend session correlation. Complex but correct. |

I went with `chrome.identity.launchWebAuthFlow` — it's the canonical Manifest V3 approach. The UX tradeoff (a Chrome-branded window) is acceptable because it's familiar to users and signals legitimacy:

```ts
// background/auth.ts
export async function initiateGoogleOAuth(): Promise<string> {
  const clientId = process.env.GOOGLE_CLIENT_ID;
  const redirectUri = chrome.identity.getRedirectURL("oauth2");
  
  const authUrl = new URL("https://accounts.google.com/o/oauth2/auth");
  authUrl.searchParams.set("client_id", clientId);
  authUrl.searchParams.set("redirect_uri", redirectUri);
  authUrl.searchParams.set("response_type", "token");
  authUrl.searchParams.set("scope", "openid email profile");
  
  const responseUrl = await chrome.identity.launchWebAuthFlow({
    url: authUrl.toString(),
    interactive: true,
  });
  
  // Extract access token from redirect URL hash
  const hash = new URL(responseUrl).hash;
  const params = new URLSearchParams(hash.substring(1));
  return params.get("access_token")!;
}
```

Why not ask for an email/password? Because managing passwords means managing hashes, reset flows, and breach liability. Google OAuth is one-click and moves the security responsibility to a provider designed for it. The tradeoff is user dependency on Google — acceptable for this use case.

## The backend: Drizzle over Prisma, and why

I use Drizzle ORM on the backend. This was a deliberate choice over Prisma:

**Prisma's model**: You write a `schema.prisma`, Prisma generates TypeScript types, and you query through a Prisma Client that abstracts SQL completely. Good for teams that want a productive abstraction.

**Drizzle's model**: You define your schema in TypeScript directly. The types ARE the schema. You write SQL-like queries that compile to actual SQL with no magic in between:

```ts
// schema.ts — Drizzle
export const ratings = pgTable("ratings", {
  id: uuid("id").primaryKey().defaultRandom(),
  hostname: varchar("hostname", { length: 255 }).notNull(),
  userId: uuid("user_id").notNull().references(() => users.id),
  stars: integer("stars").notNull(),
  review: text("review"),
  createdAt: timestamp("created_at").defaultNow(),
});

// query — you see what SQL will run
const avg = await db
  .select({
    hostname: ratings.hostname,
    avgStars: sql<number>`avg(${ratings.stars})::numeric(3,1)`,
    count: count(),
  })
  .from(ratings)
  .where(eq(ratings.hostname, targetHostname))
  .groupBy(ratings.hostname);
```

The cast `::numeric(3,1)` in the SQL is explicit — I know what precision I'm getting. With Prisma, I'd need to check documentation to understand what `_avg` returns. Drizzle stays close to the metal while giving me TypeScript safety. For a solo project where I'm both the schema designer and the query writer, this matters.

## Preventing review bombing: authenticated writes only

The hardest trust problem in community-rating systems isn't building the rating — it's preventing manipulation.

My approach:
1. Every review requires Google OAuth. Throwaway emails can create throwaway Google accounts, but the friction is much higher than anonymous rating.
2. Rate limiting by `user_id` — max 1 rating per domain per user. Implemented at the Fastify route level with a Redis counter:

```ts
async function rateLimitByUser(userId: string, hostname: string): Promise<boolean> {
  const key = `rate:${userId}:${hostname}`;
  const existing = await redis.get(key);
  if (existing) return false; // already rated
  
  await redis.setex(key, 60 * 60 * 24 * 30, "1"); // 30 days TTL
  return true;
}
```

3. Reputation weighting (WIP): accounts older than 30 days get 1.2x weight. Accounts that consistently rate outliers (always 1-star or always 5-star) get a reputation penalty.

## Tailwind v4 — what actually changed

I was on an alpha/beta of Tailwind v4 when I built this. The headline change: **no `tailwind.config.js`**. The config moves to CSS:

```css
/* globals.css */
@import "tailwindcss";

@theme {
  --color-brand: oklch(65% 0.22 280);
  --font-sans: "Inter", sans-serif;
  --radius: 8px;
}
```

The browser-native `oklch()` color space (which Tailwind v4 uses by default) is perceptually uniform — stepping from `brand-400` to `brand-500` looks consistent regardless of hue. This matters for extension UI where color conveys trust signals (green = safe, red = dangerous, yellow = caution).

## Lessons from building in the extension ecosystem

**Don't fight the message-passing model**: Extension components are isolated by design. Trying to share state across popup, content script, and background without message passing leads to brittle code. Embrace `chrome.runtime.sendMessage` / `chrome.runtime.onMessage` as the communication bus. It's verbose but explicit.

**Cache aggressively at the service worker level**: The popup opens and closes constantly. Any data that isn't in the service worker's in-memory cache will feel slow. I cache ratings for 5 minutes — stale-while-revalidate pattern.

**Manifest V3 service workers are ephemeral**: Unlike Manifest V2 background pages, service workers can be killed by Chrome. Don't rely on in-memory state surviving between sessions. Use `chrome.storage.session` for session state, `chrome.storage.local` for persistent local state.
