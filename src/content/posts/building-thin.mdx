# Introduction

I built **Thin** to be small in footprint but big in thoughtfulness. Over the last year I designed and implemented three complementary codebases: the mobile client (**Bikash9609/thin**), the backend API (**Bikash9609/thin_be**), and a Python aggregator (**Bikash9609/aggregator**) that collects and normalizes external data feeds. Together they demonstrate how I think about user experience, system decomposition, data modeling, operational reliability and pragmatic engineering trade‑offs.

This post walks through the whole system from the perspective of how I designed it, the concrete coding patterns I used, the database layout and reasoning behind it, the technical challenges I encountered, and the deliberate remedies I implemented. I’ll include small concrete examples and pseudocode to show my implementation and design thinking.

## Project overview (how the pieces fit)

- **thin** — a React Native + TypeScript mobile app (iOS and Android) that presents the user interface, handles local state, theming, and consumes the backend APIs.
- **thin_be** — the application backend that exposes HTTP JSON APIs for the mobile client: auth, data queries, and business logic.
- **aggregator** — Python services that ingest, normalize and persist datasets from external sources. These are consumed by `thin_be` or written into shared storage.

### Why this split?

I wanted a clear separation of concerns: the mobile client focuses on UX and local performance, the backend focuses on synchronous user-facing requests and business rules, and the aggregator focuses on heavyweight, asynchronous ETL that shouldn’t slow down the user experience. That separation makes it easier to scale, test and iterate on each component.

## Part I — thin (mobile client): code, structure and decisions

### Tech stack and tools

- **React Native** with TypeScript for strong typing and component contracts.
- **Metro/Babel** for bundling, **Jest** for unit tests, **ESLint/Prettier** for style consistency.
- **Native folders** for platform-specific configuration (`ios/` and `android/`), and a `Gemfile` for Ruby tooling (CocoaPods, fastlane).

### What I focused on in the code

- **Type safety**: every component and API helper uses TypeScript interfaces to force well-formed data at compile time. That reduces a huge class of runtime errors when you parse API responses.
- **Theming**: a centralized `AppThemeProvider` (themable context) so components depend on a single source of truth for colors, spacing, and accessible typography. Theme changes (light/dark) are straightforward because components read from a typed theme object.
- **Component isolation**: I prefer small, testable components with a single responsibility. Complex UI flows are composed from simple building blocks.
- **Testing**: snapshot and unit tests for pure components and utility functions. I write Jest tests to exercise business logic and parsers.

### Example (TypeScript pattern I use)

This is the kind of pattern I used to turn API data into strictly typed domain objects:

```ts
// types.ts
export interface ItemDTO {
  id: string;
  title: string;
  payload?: any;
}
export interface Item {
  id: string;
  title: string;
  data: NormalizedPayload;
}

// api.ts
async function fetchItems(): Promise<ItemDTO[]> {
  /* fetch */
}

function normalize(dto: ItemDTO): Item {
  return {
    id: dto.id,
    title: dto.title.trim(),
    data: normalizePayload(dto.payload),
  };
}

// usage in component
const items = (await fetchItems()).map(normalize);
```

### State and performance considerations

- Avoid unnecessary re-renders with memoization (`React.memo`, `useCallback`, `useMemo`).
- Use `FlatList`/`SectionList` with stable keys and `getItemLayout` where possible.
- Defer intensive parsing (JSON → domain) to background tasks when startup time is critical.

### Native integration and release tooling

- The `Gemfile` is used to centralize Ruby tooling (CocoaPods, fastlane). I automated release steps and builds with Fastlane on CI to avoid manual certificate/entitlements issues.

## Part II — thin_be (backend): API, system design, and database thinking

### Backend responsibilities

- Serve RESTful JSON endpoints to the mobile client.
- Authorize/Authenticate users, validate inputs, and enforce business logic.
- Expose aggregated datasets ingested by the aggregator.

### API design principles I applied

- **Contract-first thinking**: define request/response shapes (OpenAPI or typed interfaces) and keep the client and server contracts aligned.
- **Lean endpoints**: endpoints return only what the client needs (avoid overfetching).
- **Versioning**: `/v1/...` endpoints so we can evolve APIs without breaking clients.

### Authentication & security

- **Token-based auth** (JWT or session tokens) for stateless verification at the API edge.
- **Rate limiting** and input validation to defend against malformed requests and abuse.
- **Secrets** stored in environment variables or a secret manager; TLS for all communications.

### Database design — a concrete schema and rationale

I designed the primary data model for two use cases: user-driven content (for app features) and aggregated records (for normalized external data). Below is a condensed schema illustrating the core ideas and indexes I used.

#### Users and app data (simplified)

- `users`: id (PK, UUID), email (unique), password_hash, created_at, last_login
- `sessions`: id (PK), user_id (FK -> users.id), token, expires_at
- `items`: id (PK), owner_id (FK->users.id), title, body, created_at, updated_at

**Indexes and reason:**

- `users.email` UNIQUE — fast lookup at login.
- `items.owner_id` INDEX — efficient query to list a user’s items.

#### Aggregated data schema (the aggregator writes here)

- `sources`: id (PK), name, base_url, last_fetched_at, config (JSON)
- `aggregated_records`:
  - `id` (PK, UUID)
  - `source_id` (FK -> sources.id)
  - `external_id` (string) — the raw source ID (if present)
  - `dedupe_key` (string) — deterministic key used to deduplicate
  - `payload` (JSONB) — normalized data
  - `normalized_at` (timestamp)
  - `ingest_status` (enum: pending, success, failed)
  - `hash` (string) — content hash for change detection

**Key design choices and reasoning:**

- Use **JSONB** for payloads where fields change across sources, but shape critical fields into columns when we query them frequently (e.g., title, published_at).
- `dedupe_key` and `hash` let the system detect identical or updated records quickly.
- Index on `(source_id, dedupe_key)` and `hash` for efficient deduplication lookups.
- Use FK constraints to maintain referential integrity, and use migrations for schema changes.

#### Example SQL (Postgres)

- `aggregated_records` table indexes:
  ```sql
  CREATE UNIQUE INDEX uix_source_dedupe ON aggregated_records (source_id, dedupe_key);
  CREATE INDEX idx_hash ON aggregated_records (hash);
  ```

### Transactional logic and migrations

- I use database migrations (Flyway/Alembic/ActiveRecord) for safe schema evolution.
- Mutations that require multiple table updates are wrapped in transactions to maintain consistency.

## Part III — aggregator (Python): pipelines, idempotency, and reliability

### Purpose

The aggregator collects data from heterogenous external sources, normalizes it to a canonical shape, deduplicates, and persists it into the `aggregated_records` table described earlier. Separating ETL into its own service keeps heavy processing outside the request/response path for the mobile app.

### Design patterns I used

- **Source adapter pattern**: each data source has a small adapter that knows how to fetch and parse that source. The main pipeline invokes adapters uniformly.
- **Idempotent ingestion**: ingestion is safe to re-run (same `dedupe_key` => update, not duplicate).
- **Checkpointing and resumability**: keep `last_fetched_at` per source so we can resume after failures.
- **Retry** with exponential backoff and jitter for flaky remote APIs.

### Example ingestion pseudocode (Python)

This captures the idempotency and deduplication:

```python
def ingest_source(source):
    for raw_item in source.adapter.fetch_incremental(source.last_fetched_at):
        dedupe_key = source.adapter.make_dedupe_key(raw_item)
        normalized = source.adapter.normalize(raw_item)
        hash = compute_hash(normalized)

        with db.transaction():
            existing = db.one(
                "SELECT id, hash FROM aggregated_records WHERE source_id=%s AND dedupe_key=%s",
                (source.id, dedupe_key)
            )
            if existing:
                if existing.hash != hash:
                    db.execute("UPDATE aggregated_records SET payload=%s, hash=%s, normalized_at=NOW() WHERE id=%s",
                               (normalized, hash, existing.id))
                else:
                    # nothing changed
                    continue
            else:
                db.execute("INSERT INTO aggregated_records (id, source_id, external_id, dedupe_key, payload, hash, ingest_status, normalized_at) VALUES (...)")
```

### Scaling considerations

- I run adapters in worker pools (multiprocessing or Celery workers) and partition work by source or by partition keys to parallelize safely.
- For very large sources, stream processing and chunked writes avoid memory blowups.
- For high throughput, use bulk inserts with conflict handling (Postgres `ON CONFLICT DO UPDATE`).

### Observability and testing

- Aggregator logs each fetch, success, and failure with contextual metadata (source, job id, elapsed time).
- I add metrics (counts, latencies) exported to Prometheus and alerts for job failures or schema drift.
- Unit tests for adapter parsing, and integration tests that use recorded source payloads to ensure normalization correctness.

### Operational design — deployment, CI/CD, monitoring

- **Containerize services** for stable builds (Docker).
- **CI pipelines** run linters, unit tests, and then build artifacts. Mobile CI runs unit tests and optionally builds debug bundles; release builds require secrets in CI or manual runs through fastlane.
- **Centralized logging** and error tracking: Sentry for exceptions, Prometheus/Grafana for metrics, structured logs for business events.
- **Release practices**: migrations are deployed in a safe sequence (apply migrations, deploy service that uses new schema) and I use feature flags for risky behavior.

## Key technical challenges I faced and how I fixed them

**1. Schema drift in aggregator sources**

- **Problem**: external sources changed their JSON structure and the parser started failing.
- **Remedy**: add schema validation with expressive tests (sample payloads committed to repo) and alerting when a source’s parsing error rate spikes. Also added a lightweight adapter test harness to validate a new schema before enabling production runs.

**2. Mobile-startup latency**

- **Problem**: app took too long on first run due to heavy parsing.
- **Remedy**: defer non-critical work, lazily load large resources, and parse in a background job with progress UI. Also cached parsed blobs in local storage.

**3. Native build and signing headaches**

- **Problem**: iOS signing and provisioning errors during releases.
- **Remedy**: automated with Fastlane and CI secrets to streamline certificate deployment and avoided manual steps.

**4. Duplicate aggregated records**

- **Problem**: overlaps across feeds created duplicates.
- **Remedy**: introduced a deterministic `dedupe_key` and unique constraint on `(source_id, dedupe_key)`, plus content hashing to detect updates.

**5. Flaky third-party APIs**

- **Problem**: intermittent failures and rate-limiting.
- **Remedy**: retry strategy with exponential backoff and jitter, and fallback to cached records when absolute freshness is not required.

## What this project demonstrates about my engineering style

- I favor **clear separation of concerns** and pragmatic systems thinking: isolate heavyweight tasks (ETL) from user-facing components (API, mobile app).
- I design for **observability and resiliency** up front: logging, metrics, retries, and idempotency are in the core design.
- I write code meant to be **comprehensible** — small, testable modules backed by types and schema checks.
- I choose technologies to **minimize friction**: TypeScript for maintainability in UI, Python for ETL productivity, Postgres for reliable JSON support and transactional semantics.

### Concrete examples of my craft

- **Thoughtful TypeScript types** and normalization functions to guarantee client-side data shape.
- **Database schemas** that balance JSON flexibility (JSONB) with relational indexes for querying speed.
- **Idempotent ingestion logic** that ensures safe retries and updates.
- **CI and release automation** to reduce manual human errors and speed iteration.
