# Building Thin: Why I Split One Product Into Three Codebases

The usual instinct when building a personal product is to keep everything in one repo, one process, one deployment. It's faster to start. It's easier to reason about locally. And it's wrong — at the moment your product has more than one distinct concern with different scaling and failure characteristics.

**Thin** is a cross-platform app (iOS + Android) for aggregated content. I built three separate codebases:
- `thin` — the React Native + TypeScript mobile client
- `thin_be` — the Fastify backend API
- `aggregator` — a Python ETL service

This post is about *why* I made that split, not just *what* I built.

---

## The core architectural question

Before writing a line of code, I asked: **What are the failure modes of each part of this system, and do they share them?**

A user requesting their feed and a Python process ingesting 50,000 records from external APIs have nothing in common:

| Dimension | Mobile Client | API Backend | Aggregator |
|-----------|---------------|-------------|------------|
| Trigger | User action | HTTP request | Cron / event |
| Failure impact | UX degradation | 5xx errors | Stale data |
| Scaling axis | Devices | Request volume | Ingestion throughput |
| Performance concern | Render/parse speed | Latency / p99 | Throughput / memory |
| Language best-fit | TypeScript | TypeScript | Python |

Once you map this out, keeping them in one process becomes obviously wrong. If the aggregator crashes, it shouldn't take down the API. If a third-party source rate-limits you for 60 seconds, your users shouldn't see 504s.

Separation is not dogma. It's a consequence of these differences.

## The Mobile Client (`thin`) — TypeScript disciplines over React Native

React Native's Achilles heel is silent type drift. You fetch from an API, the shape changes slightly, and you get a blank screen instead of an error. I dealt with this by treating the API boundary as a strict contract:

```ts
// types.ts — single source of truth for API shapes
export interface FeedItemDTO {
  id: string;
  source_id: string;
  title: string;
  normalized_at: string;
  payload: Record<string, unknown>; // intentionally loose
}

export interface FeedItem {
  id: string;
  title: string;
  publishedAt: Date;
  content: NormalizedContent; // domain-specific, parsed
}

// api/parsers.ts
function parseFeedItem(dto: FeedItemDTO): FeedItem {
  return {
    id: dto.id,
    title: dto.title.trim(),
    publishedAt: new Date(dto.normalized_at),
    content: parsePayload(dto.payload),
  };
}

// usage — never use DTOs directly in components
const items = (await feedApi.getItems()).map(parseFeedItem);
```

Why maintain both `FeedItemDTO` and `FeedItem`? Because the API shape is what the *server* cares about. The domain shape is what the *UI* cares about. When the server changes its field names (and it will), you update one function — not 30 components.

### Performance on mobile is different

Browser React and React Native both use the reconciler, but the perf profile is different. On RN, JS runs on a single thread (before new arch), and bridge communication has latency. My rules:

- Never run JSON parsing on the main thread during list scroll
- Use `FlatList` with `getItemLayout` when item heights are uniform — eliminates layout calculation on scroll
- Memoize list items with `React.memo` — RN re-renders are expensive

```tsx
const FeedListItem = React.memo(({ item }: { item: FeedItem }) => {
  return <ItemView data={item} />;
}, (prev, next) => prev.item.id === next.item.id);
```

## The Backend (`thin_be`) — Fastify over Express, and why it matters

I chose Fastify over Express deliberately:

- **Schema validation built-in**: Fastify uses JSON Schema for request/response validation. Express has no native equivalent — you bolt on Zod or Joi as middleware. With Fastify, the route definition *is* the contract:

```ts
const feedRoute: RouteOptions = {
  method: "GET",
  url: "/v1/feed",
  schema: {
    querystring: { type: "object", properties: { page: { type: "integer" } } },
    response: {
      200: {
        type: "object",
        properties: {
          items: { type: "array", items: feedItemSchema },
          total: { type: "integer" },
        },
      },
    },
  },
  handler: getFeedHandler,
};
```

This is not just validation — Fastify uses the schema to serialize responses 2–3x faster than `JSON.stringify` via fast-json-stringify. That matters at scale.

- **Plugin architecture**: Fastify's plugin system with `fastify-plugin` and scoped decorators beats Express middleware ordering bugs. Auth, rate limiting, and DB clients are plugins with proper lifecycle hooks.

### Database design — thinking about query patterns upfront

The aggregator writes to `aggregated_records`. The API reads from it. Their access patterns are completely different:

**Aggregator writes**: bulk upserts, conflict resolution on `(source_id, dedupe_key)`.
**API reads**: paginated, filtered by `source_id`, ordered by `normalized_at DESC`.

The indexes I created reflect *both* access patterns:

```sql
-- For aggregator: fast conflict detection
CREATE UNIQUE INDEX uix_source_dedupe 
  ON aggregated_records (source_id, dedupe_key);

-- For API: fast paginated feed reads
CREATE INDEX idx_feed_read 
  ON aggregated_records (normalized_at DESC, ingest_status)
  WHERE ingest_status = 'success';

-- Content hash for change detection (aggregator)
CREATE INDEX idx_hash ON aggregated_records (hash);
```

`WHERE ingest_status = 'success'` is a partial index — it only indexes rows the API will actually query. This is ~40% smaller than indexing the whole table.

## The Aggregator (`aggregator`) — Python, not Node, and here's why

I write Node.js every day. I know it well. I still chose Python for the aggregator. Here's the reasoning:

- **Async I/O isn't the bottleneck here**: The aggregator's hot path is CPU-bound parsing and normalization — HTML scraping, XML parsing, data transformation. Node's single-threaded event loop excels at I/O concurrency, not CPU work. Python with `multiprocessing` maps naturally to parallel source processing.

- **Ecosystem**: `lxml` for fast XML, `httpx` for async HTTP with HTTP/2, `pydantic` for strict data validation, `celery` for task queue. The Python data ecosystem is deeper for ETL workloads.

- **The source adapter pattern**: Each data source is an adapter class with a consistent interface:

```python
class BaseAdapter(ABC):
    @abstractmethod
    def fetch_incremental(self, since: datetime) -> Iterator[RawItem]:
        ...
    
    @abstractmethod
    def make_dedupe_key(self, raw: RawItem) -> str:
        ...
    
    @abstractmethod
    def normalize(self, raw: RawItem) -> NormalizedPayload:
        ...
```

Adding a new source = one new adapter class. The pipeline loop never changes.

### Idempotent ingestion — the most important design decision

The aggregator runs on a schedule. Network is unreliable. Sources have partial failures. The pipeline must be safe to re-run at any time without creating duplicates or losing data:

```python
def ingest_item(source: Source, raw: RawItem, db: Database) -> None:
    dedupe_key = source.adapter.make_dedupe_key(raw)
    normalized = source.adapter.normalize(raw)
    content_hash = sha256(json.dumps(normalized, sort_keys=True))
    
    with db.transaction():
        existing = db.fetchone(
            "SELECT id, hash FROM aggregated_records "
            "WHERE source_id = %s AND dedupe_key = %s",
            (source.id, dedupe_key)
        )
        
        if existing is None:
            # New record
            db.execute("INSERT INTO aggregated_records ...")
        elif existing.hash != content_hash:
            # Content changed — update, don't duplicate
            db.execute(
                "UPDATE aggregated_records SET payload = %s, hash = %s, "
                "normalized_at = NOW() WHERE id = %s",
                (normalized, content_hash, existing.id)
            )
        # else: identical content, skip (fast path)
```

The `content_hash` comparison is what makes this truly idempotent. Not just deduplication by key, but deduplication by *content* — so re-ingesting unchanged records is effectively a no-op.

## Operational Design

### Observability from day one

I didn't add metrics "later." Each pipeline run logs structured JSON:

```python
logger.info("ingest.complete", extra={
    "source": source.name,
    "fetched": fetched_count,
    "inserted": inserted_count,
    "updated": updated_count,
    "skipped": skipped_count,
    "duration_ms": elapsed,
    "error_rate": errors / fetched_count,
})
```

Structured logs are queryable. When something breaks, I can filter by `source`, join on `error_rate > 0.1`, and immediately know which adapter is failing and why.

### Retry strategy

Third-party APIs fail. My retry logic is exponential backoff with jitter — not naive linear retry:

```python
def with_retry(fn, max_retries=3, base_delay=1.0):
    for attempt in range(max_retries):
        try:
            return fn()
        except (RequestError, RateLimitError) as e:
            if attempt == max_retries - 1:
                raise
            # Exponential backoff + jitter to prevent thundering herd
            delay = base_delay * (2 ** attempt) + random.uniform(0, 1)
            time.sleep(delay)
```

The jitter is not an afterthought. When multiple adapters fail simultaneously (source goes down) and all retry at the same time, they cause a thundering herd that overwhelms both the source and your own infrastructure. Jitter distributes the retry load.

## What the split cost me vs. what it earned me

**Cost**: Three separate Docker images. Three separate test suites. Three `.env` files. More CI configuration.

**Earned**: The aggregator crashed twice during development due to memory issues processing large XML feeds. The API stayed up. Users saw slightly stale data — not errors. That's the value of the split.

When the Gopher Go migration had a bug in the Node.js microservice at my day job, we isolated it to one service and hotfixed it without touching the React Native client or any other service. Same principle, same benefit.

Separation of concerns is not an academic principle. It's a reliability strategy.
