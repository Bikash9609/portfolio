# Thin: Deconstructing Monolithic Architectures for Multi-Platform Reliability

The conventional approach for rapid product iteration favors monolithic architectures: a single repository, a unified deployment process, and shared memory space. While advantageous for initial velocity, this model becomes a liability the moment a system develops discrete operational concerns with divergent failure modes and scaling characteristics.

**Thin** is a cross-platform mobile application (iOS + Android) designed for high-throughput content aggregation. To ensure maximum reliability and operational flexibility, the system was decoupled into three highly specialized codebases:
- `thin` — A strictly typed React Native client
- `thin_be` — A highly concurrent Fastify backend API
- `aggregator` — A robust Python ETL (Extract, Transform, Load) service

This document details the engineering rationale behind this distributed architecture.

---

## Architectural Isolation: Mapping Failure Domains

Before implementation, the system was mapped according to its failure modes and scaling vectors. 

An end-user requesting a mobile feed and an asynchronous ETL process ingesting 50,000 external records share no operational characteristics:

| Dimension | Mobile Client | API Backend | Aggregator (ETL) |
|-----------|---------------|-------------|------------------|
| Trigger | Synchronous UI action | Synchronous HTTP | Scheduled Cron / Event-driven |
| Failure Impact | Local UX degradation | Global 5xx errors | Stale data ingestion |
| Scaling Axis | Active Devices | Request throughput (RPS) | Payload volume / Ingestion concurrency |
| Primary Constraint| Main-thread execution time | P99 Latency | CPU processing / Memory consumption |
| Tech Stack | TypeScript / React Native | TypeScript / Fastify | Python |

Isolating these domains is not an academic exercise in microservices; it is a fundamental reliability requirement. If the ETL aggregator exhausts memory during a massive data ingestion phase, it must not trigger cascading failures that result in 504 Gateway Timeouts for active mobile users.

## The Mobile Client (`thin`): Enforcing Strict Contracts in React Native

A critical vulnerability in React Native development is silent type drift across network boundaries. When an API payload mutates unexpectedly, the UI layer frequently encounters unhandled runtime exceptions resulting in fatal application crashes (white screens). 

Thin mitigates this by enforcing strict Data Transfer Object (DTO) parsing at the network boundary:

```ts
// types.ts — Immutable API contract definitions
export interface FeedItemDTO {
  id: string;
  source_id: string;
  title: string;
  normalized_at: string;
  payload: Record<string, unknown>; // Intentionally opaque for flexible parsing
}

export interface FeedItem {
  id: string;
  title: string;
  publishedAt: Date;
  content: NormalizedContent; // Domain-specific, fully validated entity
}

// api/parsers.ts — The Anti-Corruption Layer
function parseFeedItem(dto: FeedItemDTO): FeedItem {
  return {
    id: dto.id,
    title: dto.title.trim(),
    publishedAt: new Date(dto.normalized_at),
    content: parsePayload(dto.payload),
  };
}

// UI implementation — Components exclusively consume validated domain entities
const items = (await feedApi.getItems()).map(parseFeedItem);
```

By explicitly decoupling the `FeedItemDTO` (the wire format) from the `FeedItem` (the UI domain model), the system localizes network mutations. When backend payload structures evolve, engineers update a single parser function rather than tracing and modifying dozens of disparate React components.

### Performance Considerations for React Native

React Native's architecture executes JavaScript on a single thread. CPU-intensive operations block UI rendering, leading to dropped frames during list scrolling. The application enforces strict performance mandates:

- JSON parsing and complex object manipulation are strictly prohibited on the main thread during scroll events.
- Heavy reliance on `FlatList` with `getItemLayout` for deterministic height calculation, bypassing dynamic layout rendering during scroll.
- Aggressive memoization of list items utilizing `React.memo` to prevent redundant bridge communication.

```tsx
const FeedListItem = React.memo(({ item }: { item: FeedItem }) => {
  return <ItemView data={item} />;
}, (prev, next) => prev.item.id === next.item.id);
```

## The Backend API (`thin_be`): Fastify for High Concurrency

Fastify was selected over Express to power the backend API due to its superior request throughput and native schema validation:

- **Integrated Schema Validation**: Fastify utilizes JSON Schema natively for both request validation and response serialization. In legacy frameworks, validation is often relegated to bolt-on middleware. With Fastify, the route definition acts as an immutable contract:

```ts
const feedRoute: RouteOptions = {
  method: "GET",
  url: "/v1/feed",
  schema: {
    querystring: { type: "object", properties: { page: { type: "integer" } } },
    response: {
      200: {
        type: "object",
        properties: {
          items: { type: "array", items: feedItemSchema },
          total: { type: "integer" },
        },
      },
    },
  },
  handler: getFeedHandler,
};
```

This architecture provides a dual benefit: strict input validation and accelerated response serialization. Fastify compiles the schema into highly optimized serialization functions, outperforming native `JSON.stringify` by 2–3x under load.

### Database Architecture: Optimizing Divergent Access Patterns

The central database table, `aggregated_records`, serves two distinct consumers with conflicting access patterns:

**Aggregator (Write-Heavy)**: Executes high-volume bulk upserts, requiring rapid conflict resolution on `(source_id, dedupe_key)`.
**API (Read-Heavy)**: Executes paginated reads, filtered heavily by `source_id` and sorted chronologically by `normalized_at DESC`.

The database indexing strategy isolates these concerns to maintain consistent performance:

```sql
-- Write-optimization for ETL conflict detection
CREATE UNIQUE INDEX uix_source_dedupe 
  ON aggregated_records (source_id, dedupe_key);

-- Read-optimization for API feed generation (Partial Index)
CREATE INDEX idx_feed_read 
  ON aggregated_records (normalized_at DESC, ingest_status)
  WHERE ingest_status = 'success';

-- Content hash indexing for idempotent ETL updates
CREATE INDEX idx_hash ON aggregated_records (hash);
```

The partial index (`WHERE ingest_status = 'success'`) is particularly critical; it indexes solely the data required by the API, resulting in a substantially smaller index footprint and significantly faster cache hits in PostgreSQL.

## The ETL Aggregator (`aggregator`): Python for Heavy Data Pipelines

Despite extensive organizational expertise in Node.js, Python was explicitly selected for the ETL pipeline. 

- **CPU-Bound Processing**: The aggregator's critical path involves dense HTML scraping, XML traversal, and data normalization. Node.js's single-threaded event loop excels at concurrent I/O but stalls under heavy synchronous CPU loads. Python's `multiprocessing` architecture maps naturally to parallelized data processing.
- **Ecosystem Maturity**: Python's data ecosystem—`lxml` for optimized XML parsing, `httpx` for multiplexed HTTP/2, `pydantic` for strict payload validation, and `celery` for distributed task queues—provides unmatched tooling for robust ETL development.

### Idempotent Ingestion: Preventing Data Corruption

ETL pipelines operate in hostile environments characterized by network unreliability, partial source failures, and unpredictable data mutation. The pipeline must guarantee safe, idempotent re-execution at any given time without introducing duplicate records:

```python
def ingest_item(source: Source, raw: RawItem, db: Database) -> None:
    dedupe_key = source.adapter.make_dedupe_key(raw)
    normalized = source.adapter.normalize(raw)
    content_hash = sha256(json.dumps(normalized, sort_keys=True))
    
    with db.transaction():
        existing = db.fetchone(
            "SELECT id, hash FROM aggregated_records "
            "WHERE source_id = %s AND dedupe_key = %s",
            (source.id, dedupe_key)
        )
        
        if existing is None:
            # Insert net-new record
            db.execute("INSERT INTO aggregated_records ...")
        elif existing.hash != content_hash:
            # Content drift detected — update existing record
            db.execute(
                "UPDATE aggregated_records SET payload = %s, hash = %s, "
                "normalized_at = NOW() WHERE id = %s",
                (normalized, content_hash, existing.id)
            )
        # Identical hash: Fast-path skip, no database mutation required
```

Hashing the normalized payload ensures deduplication is determined by absolute content state, not merely by primary key presence.

## Operational Resilience

### Structured Observability

Telemetry is integrated as a primary requirement. Every pipeline execution emits structured, queryable logs:

```python
logger.info("ingest.complete", extra={
    "source": source.name,
    "fetched": fetched_count,
    "inserted": inserted_count,
    "updated": updated_count,
    "skipped": skipped_count,
    "duration_ms": elapsed,
    "error_rate": errors / fetched_count,
})
```

When ingestion anomalies occur, operational teams can instantly filter by `error_rate > 0.1` to isolate the failing external source adapter without manual log scraping.

### Exponential Backoff with Jitter

To prevent systemic failures during external API outages, the aggregator implements strict exponential backoff paired with randomized jitter:

```python
def with_retry(fn, max_retries=3, base_delay=1.0):
    for attempt in range(max_retries):
        try:
            return fn()
        except (RequestError, RateLimitError) as e:
            if attempt == max_retries - 1:
                raise
            # Exponential backoff + jitter mitigates thundering herd scenarios
            delay = base_delay * (2 ** attempt) + random.uniform(0, 1)
            time.sleep(delay)
```

Without jitter, multiple failing concurrent tasks will synchronize their retries, creating a "thundering herd" that overwhelms upstream providers and local network interfaces simultaneously.

## Conclusion

Distributing the architecture required managing independent Docker orchestrations, maintaining multiple CI pipelines, and writing cross-language integration tests. 

However, when a severe memory leak occurred during the parsing of a malformed 200MB XML feed, the Python aggregator safely crashed and restarted while the Fastify API maintained a 100% uptime SLA for mobile clients. The users experienced slightly stale content, rather than cascading application failures. 

Architectural separation of concerns is not merely an academic design pattern; it is a foundational prerequisite for enterprise reliability.
