# Designing a Scalable Chat Backend Architecture

Developing a real-time chat application appears deceptively simple at the prototype phase. A basic WebSocket server maintaining an in-memory array of connections suffices for a handful of users. However, scaling that architecture to support thousands of concurrent connections distributed across multiple geographical regions introduces severe engineering complexity.

The **Origin Chat Backend** was architected to solve these precise scaling challenges. Built with TypeScript and containerized via Docker, the system is designed to be completely stateless, allowing for infinite horizontal scaling and robust fault tolerance.

## The Problem with Stateful WebSockets

The fundamental challenge with WebSocket connections is their stateful nature. Once a client connects to `Server A`, a persistent TCP tunnel is established. If `User 1` connects to `Server A` and `User 2` connects to `Server B`, a message sent by `User 1` will never reach `User 2` unless `Server A` has a mechanism to communicate with `Server B`.

Relying on in-memory state for active connections or message routing inevitably leads to a monolithic architecture that cannot be load-balanced effectively.

## The Stateless Architecture: Redis Pub/Sub

To achieve true horizontal scalability, the Origin Chat Backend decouples connection management from message distribution utilizing a centralized message broker: **Redis Pub/Sub**.

### The Message Routing Flow

1. **Connection**: A client establishes a WebSocket connection with any available backend instance (e.g., `Instance A`), managed via a standard reverse proxy load balancer.
2. **Subscription**: Upon successful authentication, `Instance A` subscribes to a specific Redis channel corresponding to the chat room the user has joined (e.g., `room:1234`).
3. **Publishing**: When the user sends a message, `Instance A` validates and persists the message to the primary database (PostgreSQL), then publishes the payload to the Redis channel `room:1234`.
4. **Distribution**: Redis broadcasts this message to *all* backend instances subscribed to that channel.
5. **Delivery**: Every instance receives the broadcast, checks its local registry of active WebSocket connections, and forwards the message to any connected clients participating in `room:1234`.

```ts
// Example: Publishing and Subscribing via Redis
import { Redis } from "ioredis";
import { WebSocket } from "ws";

const redisPub = new Redis(process.env.REDIS_URL);
const redisSub = new Redis(process.env.REDIS_URL);

// Subscribe to a room channel
export async function subscribeToRoom(roomId: string, socket: WebSocket) {
  const channel = `room:${roomId}`;
  
  // Register local connection
  connectionManager.add(roomId, socket);
  
  // Subscribe Redis client (idempotent operation)
  await redisSub.subscribe(channel);
}

// Global message listener
redisSub.on("message", (channel, messagePayload) => {
  const roomId = channel.split(":")[1];
  const sockets = connectionManager.get(roomId);
  
  // Distribute to all local connections in this room
  sockets?.forEach(socket => {
    socket.send(messagePayload);
  });
});

// Broadcast a new message
export async function broadcastMessage(roomId: string, payload: any) {
  const channel = `room:${roomId}`;
  await redisPub.publish(channel, JSON.stringify(payload));
}
```

This architecture renders the backend instances completely stateless regarding message routing. An instance can crash or be terminated by the orchestrator (Kubernetes) without disrupting global message delivery. Connected clients simply reconnect to a healthy instance and resume activity.

## Ensuring Delivery Guarantees

While Redis Pub/Sub provides extremely low-latency message distribution, it is fundamentally a "fire-and-forget" mechanism. If a backend instance is momentarily disconnected from Redis during a broadcast, messages will be lost.

To guarantee message delivery and maintain strict chronological ordering, the architecture employs the primary database as the absolute source of truth.

1. **Persistence First**: Before any message is published to Redis, it is committed to PostgreSQL with a strict, monotonically increasing timestamp or sequence ID.
2. **Client-Side Sync**: When a client connects or reconnects after an interruption, it does not rely solely on the WebSocket stream. It performs an initial HTTP GET request to fetch the definitive message history up to its last known sequence ID.
3. **Idempotency**: Clients maintain a cache of recently received message IDs to discard potential duplicates generated by network retries.

## Containerization and Deployment Strategy

The entire service is strictly containerized using Docker, ensuring absolute parity between local development, staging, and production environments. 

```dockerfile
# Multi-stage Docker build for optimized image size
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --only=production
COPY --from=builder /app/dist ./dist

# Execute via PM2 or native Node cluster mode
CMD ["node", "dist/server.js"]
```

This multi-stage build significantly reduces the final image size, minimizing deployment times and decreasing the attack surface by omitting development dependencies and source code.

## Conclusion

The **Origin Chat Backend** illustrates that building scalable real-time systems requires a fundamental shift away from stateful memory management. By leveraging TypeScript for strict typing, Redis Pub/Sub for distributed message brokering, and PostgreSQL for absolute data consistency, the architecture provides a highly resilient, enterprise-grade foundation for real-time communication.
