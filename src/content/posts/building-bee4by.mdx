# Building VehicleForum (Bee4By): Designing for Trust, Not Just Features

Community forums sound like solved problems. Post, comment, upvote, moderate. The CRUD is trivial. The hard part is trust: making users feel safe submitting content, making readers feel safe consuming it, and making the system resilient enough to stay up when people actually use it.

VehicleForum (Bee4By) is a niche community for vehicle owners — Q&A, maintenance tips, modification discussions, grouped by make/model. This is a walkthrough of the decisions that mattered most, and why.

---

## Why niche beats general

The temptation with forums is to build horizontally — any topic, any user. Reddit already exists. The valuable opportunity is depth: a forum specifically for vehicle owners has fundamentally different content than a general Q&A.

Vehicle make/model tagging enables a query pattern impossible on Reddit: "Show me everything about my 2008 Toyota Corolla with at least 3 upvotes from users who've owned the same car for 2+ years." That's a trust signal impossible to replicate without domain-specific data modeling.

The `Post` entity reflects this from the start:

```ts
export interface Post {
  id: string;
  authorId: string;
  title: string;
  body: string;                          // markdown
  vehicleTags: VehicleTag[];            // [{ make: "Toyota", model: "Corolla", year: 2008 }]
  images: string[];                      // CDN URLs, not data
  createdAt: string;
  upvotes: number;
  commentsCount: number;
  status: "active" | "flagged" | "archived";
  resolvedAt?: string;                   // marks accepted solution
}

export interface VehicleTag {
  make: string;
  model: string;
  year?: number;
}
```

Why `vehicleTags` as an array? A user asking about a drivetrain issue might be relevant to both a 2008 and 2009 Corolla with identical drivetrains. Allowing multiple tags means better discoverability without creating duplicate posts.

## Data model: where to use documents vs. relations

I chose **PostgreSQL** over MongoDB for this project. Here's the reasoning, because this matters:

- Posts have predictable shapes. The variability (vehicle tags, optional images) fits well in `JSONB` columns or simple optional fields — I don't need a document store for this.
- Comments form a DAG. Postgres handles the parent-child query efficiently; MongoDB nested documents hit limits at depth.
- Transactions matter: when a user upvotes, I need to atomically increment `posts.upvotes` AND update a `user_upvotes` junction table to prevent double-voting. MongoDB multi-document transactions are available but Postgres handles this more naturally.
- I want `GROUP BY` vehicle make/model for analytics. This is simple SQL; it's a MapReduce job in MongoDB.

The one place I used `JSONB` was `vehicle_tags` on the `posts` table — because the make/model structure is nested and query patterns are by individual fields, not across the whole array:

```sql
-- Efficient query for all posts tagged with Toyota Corolla
SELECT * FROM posts
WHERE vehicle_tags @> '[{"make": "Toyota", "model": "Corolla"}]'::jsonb
AND status = 'active'
ORDER BY created_at DESC
LIMIT 20;

-- Index to make this fast
CREATE INDEX idx_posts_vehicle_tags 
  ON posts USING GIN(vehicle_tags jsonb_path_ops);
```

`GIN` (Generalized Inverted Index) is specifically designed for containment queries (`@>`) on JSONB. A B-tree index doesn't work here. This is the kind of thing that separates production databases from tutorial databases.

## Image uploads: the signed URL pattern

Routing images through your application server is one of the most common performance mistakes in web development:

```
❌ Bad:  Browser → Your Server (process/store file) → S3
✓ Good: Browser → S3/Cloudinary directly (signed upload URL)
        Browser → Your Server (confirm upload, save CDN URL)
```

The second pattern:
1. Your server generates a short-lived signed upload URL (AWS S3 presigned URL or Cloudinary upload signature)
2. Browser uploads directly to the CDN — your server never touches the file bytes
3. Browser confirms the upload to your server; you save the resulting CDN URL

```ts
// Backend: generate presigned URL
async function getUploadUrl(req: FastifyRequest, reply: FastifyReply) {
  const { filename, contentType } = req.body as { filename: string; contentType: string };
  
  // Validate content type — only accept image/* types
  if (!contentType.startsWith("image/")) {
    return reply.status(400).send({ error: "Only image uploads are allowed" });
  }
  
  const key = `posts/${req.user.id}/${Date.now()}-${sanitizeFilename(filename)}`;
  
  const command = new PutObjectCommand({
    Bucket: process.env.S3_BUCKET!,
    Key: key,
    ContentType: contentType,
    // Enforce max size at S3 level
    Conditions: [["content-length-range", 0, 10_000_000]], // 10MB max
  });
  
  const presignedUrl = await getSignedUrl(s3Client, command, { expiresIn: 300 });
  const cdnUrl = `${process.env.CDN_BASE_URL}/${key}`;
  
  return { uploadUrl: presignedUrl, cdnUrl };
}
```

This pattern:
- Your server handles zero file bytes — no bandwidth cost, no memory pressure
- The 10MB limit is enforced by S3 before any bytes are transferred to S3 — not by your server checking `Content-Length`
- URL expires in 5 minutes — prevents presigned URL reuse

### Client-side compression before upload

Even with direct-to-CDN uploads, mobile devices can produce 8MB photos. I compress on the client before the presigned URL fetch:

```ts
async function compressAndUpload(file: File): Promise<string> {
  const compressed = await imageCompression(file, {
    maxSizeMB: 2,
    maxWidthOrHeight: 1920,
    useWebWorker: true, // don't block the main thread
  });
  
  const { uploadUrl, cdnUrl } = await api.getUploadUrl({
    filename: file.name,
    contentType: compressed.type,
  });
  
  await fetch(uploadUrl, {
    method: "PUT",
    body: compressed,
    headers: { "Content-Type": compressed.type },
  });
  
  return cdnUrl;
}
```

`useWebWorker: true` is not optional — compression is CPU-intensive and will visibly freeze the UI on mobile if you run it on the main thread.

## Trust mechanisms: beyond "add moderation"

"Add moderation" is not a strategy. Here's what I actually implemented:

### Idempotent post creation

Users on mobile with poor connections hit "Post" multiple times. Naive handler = duplicate posts. Solution: **idempotency keys**:

```ts
// Client includes a random idempotency key with each create request
const createPost = async (payload: CreatePostPayload) => {
  const idempotencyKey = crypto.randomUUID();
  return api.post("/posts", payload, {
    headers: { "Idempotency-Key": idempotencyKey },
  });
};

// Server uses the key to deduplicate
async function createPostHandler(req, reply) {
  const key = req.headers["idempotency-key"];
  
  // Check if this key was already processed
  const cached = await redis.get(`idem:${key}`);
  if (cached) {
    return JSON.parse(cached); // return the original response
  }
  
  const post = await db.posts.create({ data: req.body });
  
  // Cache the response for 24 hours
  await redis.setex(`idem:${key}`, 86400, JSON.stringify(post));
  
  return post;
}
```

This is safer than "disable the button after click" — that fails when JavaScript errors mid-request.

### Rate limiting with Redis sliding window

```ts
// 5 posts per user per hour — sliding window, not fixed bucket
async function rateLimitPosts(userId: string): Promise<boolean> {
  const key = `rate:posts:${userId}`;
  const now = Date.now();
  const windowMs = 60 * 60 * 1000; // 1 hour
  
  const pipeline = redis.pipeline();
  pipeline.zadd(key, now, `${now}`);              // add current timestamp
  pipeline.zremrangebyscore(key, 0, now - windowMs); // remove old entries
  pipeline.zcard(key);                             // count in window
  pipeline.expire(key, 3600);                     // TTL cleanup
  
  const results = await pipeline.exec();
  const count = results[2][1] as number;
  
  return count <= 5;
}
```

Sliding window (using a sorted set with timestamps as scores) is more accurate than a fixed bucket. A fixed bucket allows bursting at window boundaries — 5 posts at 11:59 and 5 more at 12:00. The sliding window prevents this.

## Search: why I deferred Algolia and used Postgres full-text search first

Algolia is excellent. It's also $50/month for a hobby project. I started with Postgres full-text search:

```sql
-- Add a generated tsvector column
ALTER TABLE posts ADD COLUMN search_vector tsvector 
  GENERATED ALWAYS AS (
    to_tsvector('english', 
      coalesce(title, '') || ' ' || 
      coalesce(body, '')
    )
  ) STORED;

CREATE INDEX idx_posts_fts ON posts USING GIN(search_vector);

-- Query
SELECT id, title, ts_rank(search_vector, query) AS rank
FROM posts, to_tsquery('english', 'brake AND noise') query
WHERE search_vector @@ query AND status = 'active'
ORDER BY rank DESC
LIMIT 20;
```

Postgres FTS handles stemming (`brake` matches `brakes`, `braking`), stop words, and ranking. It's not Algolia — no typo tolerance, no synonyms — but it covers 80% of use cases with zero external dependencies and zero additional cost.

I'd migrate to Algolia when search query latency exceeds 500ms or search quality noticeably impacts engagement metrics. Not before.

## What I delegated and why

| Problem | Delegated to | Why not build it |
|---------|-------------|------------------|
| Auth | NextAuth (Google + GitHub OAuth) | Session security, token rotation, PKCE — these are solved hard problems. Reinventing them creates attack surface. |
| Images | S3 + CloudFront | Storage, CDN, global delivery — not core product value. |
| Email | Resend | Transactional email deliverability is a full-time job. |
| Search | Postgres FTS (→ Algolia later) | Postgres handles early stage; migrate when constraints appear. |

The pattern: **delegate anything where failure means a security incident or reliability problem you're not equipped to handle**. Build everything that is core product differentiation.

## Lessons

**Niche communities need domain-specific data models**: Vehicle tags aren't just a string field — they're structured data that enables the queries that make the forum valuable.

**Trust mechanisms compound**: idempotency + rate limiting + authenticated writes create multiple overlapping layers. Any single layer can be bypassed; together they're effective.

**Postgres is underrated**: GIN indexes on JSONB, full-text search, window functions, advisory locks — Postgres handles the majority of use cases that teams reach for Redis, Elasticsearch, or MongoDB for. Know the tool you have before adding a new one.
