# Building an Autonomous Deep Research Agent

Most RAG implementations deployed today are essentially glorified `SELECT * WHERE embedding NEAR ?`. A query is ingested, chunks are retrieved, and an LLM summarizes the context. That's retrieval — not research. True research is an iterative process. It involves forming a hypothesis, testing it against evidence, recognizing contradictions, drilling deeper, and synthesizing across multiple contexts. 

**DdiverRAG** is a stateful autonomous research agent built on LangGraph designed for production-scale cognitive tasks. This post is an architectural walkthrough — covering the decisions, the graph design, and why standard RAG patterns fall short for non-trivial, enterprise problems.

---

## Why standard RAG fails for deep research

RAG (Retrieval-Augmented Generation) was a breakthrough for question-answering over static documents. But it carries hard assumptions that limit its utility:

- **One-shot execution**: Query → retrieve k chunks → LLM responds. There is no second pass.
- **Statelessness**: Each invocation retains no memory of the prior context loop.
- **Blind trust**: Retrieved text is treated as ground truth, not as evidence to be evaluated and cross-referenced.

For shallow Q&A, these constraints are acceptable. For deep research — where topics interconnect, sources conflict, and "I don't know enough yet" is a valid intermediate state — these assumptions break down immediately.

The core insight driving this architecture: **research is a process of managed uncertainty, not a single-pass lookup**.

---

## The Architecture: LangGraph State Graph

I selected [LangGraph](https://langchain-ai.github.io/langgraph/) because it models complex workflows as directed graphs with persistent, stateful memory. This maps perfectly to how cognitive tasks operate — moving iteratively in cycles rather than linearly from question to answer.

The agent's graph comprises four core nodes:

```text
[PLAN] → [EXECUTE] → [BELIEVE] → [REFLECT]
                          ↑              ↓
                          └──────────────┘
                        (loop while entropy > threshold)
                                   ↓
                              [SYNTHESIZE]
```

Each node operates on the full `AgentState` object — a typed dataclass that persists across execution cycles:

```python
@dataclass
class AgentState:
    query: str
    sub_questions: list[str]       # Generated by PLAN
    tool_outputs: list[ToolOutput] # Accumulated by EXECUTE
    belief_state: BeliefState      # Updated each cycle
    entropy: float                 # Calculated uncertainty measure
    iteration: int
    final_answer: str | None
```

The graph loops continuously until `entropy < 0.25` or it hits a circuit breaker (`iteration > 5`). This is the key departure from standard, linear RAG pipelines.

## The Belief State: Modeling Cognitive Confidence

The `BeliefState` is not just short-term memory — it serves as the agent's running hypothesis. After each `EXECUTE` cycle, the reasoning model updates this state:

```python
class BeliefState(TypedDict):
    hypothesis: str           # Current best synthesized answer
    confidence: float         # 0.0–1.0 probability score
    supporting_evidence: list[str]
    conflicting_evidence: list[str]
    knowledge_gaps: list[str] # Explicitly identified missing information
```

Why model state this way? Because it forces the language model to explicitly track **what it believes versus what remains uncertain**. Without this structure, LLMs confidently hallucinate when they lack information. With a typed `BeliefState`, the model is forced to declare knowledge gaps — and the graph orchestration uses those exact gaps to drive the next search iteration.

## Entropy: The Curiosity Signal

Entropy, in this architecture, acts as a proxy for **uncertainty** — borrowed loosely from information theory. It is calculated dynamically from the belief state:

```python
async def update_belief(state: AgentState, config: RunnableConfig):
    prompt = build_belief_update_prompt(state)
    response = await llm.ainvoke([HumanMessage(content=prompt)], config)
    
    new_belief: BeliefState = parse_belief_response(response.content)
    
    # Entropy scales with:
    # - Low confidence scores
    # - High volume of conflicting evidence
    # - Unresolved knowledge gaps
    new_entropy = compute_entropy(new_belief)
    
    return {"belief_state": new_belief, "entropy": new_entropy}

def compute_entropy(belief: BeliefState) -> float:
    confidence_term = 1.0 - belief["confidence"]
    conflict_term = min(len(belief["conflicting_evidence"]) * 0.15, 0.4)
    gap_term = min(len(belief["knowledge_gaps"]) * 0.1, 0.3)
    return min(confidence_term + conflict_term + gap_term, 1.0)
```

High entropy dictates that research must continue. Low entropy signals readiness to synthesize and return. This creates a **curiosity signal** — the agent keeps searching not because it is executing a rigid loop, but because its own calculated uncertainty drives it.

## The PLAN Node: Query Decomposition

Before initiating any retrieval, the agent decomposes the broad original query into targeted, highly specific sub-questions:

```python
async def plan(state: AgentState, config: RunnableConfig):
    prompt = f"""
    Research query: {state.query}
    
    Decompose this into 3-5 specific sub-questions that, when answered together,
    would allow you to fully address the original query.
    Return a JSON list of strings.
    """
    response = await llm.ainvoke([HumanMessage(content=prompt)], config)
    return {"sub_questions": parse_json_list(response.content)}
```

This decomposition phase is critical. A single broad query is a terrible search input. "What are the implications of AI on software engineering jobs?" generates high noise. Breaking it into "What specific tasks are being automated by Copilot-like tools?" and "What do economists project regarding net job displacement in software?" yields significantly higher signal-to-noise ratios during retrieval.

## The EXECUTE Node: Parallel Tool Orchestration

The agent orchestrates multiple tools, including a `search_web` API and a `visit_page` custom headless browser scraper. For each sub-question residing in `knowledge_gaps`, it executes tools in parallel:

```python
async def execute(state: AgentState, config: RunnableConfig):
    questions_to_research = state.belief_state.get("knowledge_gaps", state.sub_questions)
    
    async def process_question(question):
        results = await search_tool.ainvoke({"query": question})
        page_tasks = [visit_page_tool.ainvoke({"url": res.url}) for res in results[:2]]
        pages = await asyncio.gather(*page_tasks)
        return [ToolOutput(question=question, source=results[i].url, content=page[:3000]) for i, page in enumerate(pages)]
    
    # Cap parallel execution to prevent rate limiting
    batches = await asyncio.gather(*[process_question(q) for q in questions_to_research[:3]])
    new_outputs = [item for sublist in batches for item in sublist]
    
    return {"tool_outputs": state.tool_outputs + new_outputs}
```

Note the implementation of `asyncio.gather`. Orchestrating these network-bound tasks in parallel ensures the agent scales effectively, allowing it to ingest thousands of tokens across multiple sources within seconds.

## Semantic Storage

Between cycles, tool outputs are embedded and indexed into a vector database (such as Pinecone or Milvus). Before each `EXECUTE` cycle, the agent retrieves relevant context from previous cycles to prevent redundant fetching:

```python
# Embed and store each new tool output for persistent memory
await vector_db.add_documents(
    documents=[output.content for output in new_outputs],
    metadata=[{"source": output.source, "question": output.question} for output in new_outputs],
    ids=[generate_id(output) for output in new_outputs]
)

# Retrieve relevant past context for the current evaluation cycle
past_context = await vector_db.similarity_search(
    query=state.query,
    k=5
)
```

This design guarantees that the agent cross-references earlier findings during later synthesis without hitting external APIs redundantly.

## Tech Stack Choices — and Why

| Component | Choice | Rationale |
|-----------|--------|-----------|
| Orchestration | LangGraph | Traditional LangChain chains cannot handle stateful looping. LangGraph provides typed state and conditional edges essential for cognitive architectures. |
| Vector Store | Pinecone / Milvus | Cloud-native vector databases provide the scale and persistence required when agents run continuous, long-running research sessions. |
| LLM | OpenAI GPT-4o / Claude 3.5 Sonnet | Frontier models are required for the complex reasoning and JSON output structuring demanded by the Belief State updates. |
| Backend | FastAPI | A stateless HTTP interface over the graph. FastAPI's async primitives integrate perfectly with LangChain's `ainvoke` and parallel execution. |

---

## Looking Ahead

- **Recursive Sub-Agents**: For massive research tasks (e.g., "Write a comprehensive market analysis on X"), I plan to spawn specialized sub-agents per section, each running their own belief-entropy loop, merged later by a central coordinator.
- **Source Credibility Scoring**: Not all data is equal. Introducing a credibility heuristic to `ToolOutput` will allow the entropy calculation to weight highly-trusted sources (e.g., official docs, academic papers) over generic web pages.

---

## Takeaway

Building this agent highlighted that the primary challenge in autonomous AI isn't the underlying language model — it's the **orchestration logic** that decides when to stop, when to doubt, and when to dig deeper. The Belief State + Entropy approach equips the agent with genuine epistemic humility. It doesn't guess when it lacks context; it actively seeks to reduce its own uncertainty.

That distinction — between an agent that responds confidently and one that reasons correctly — is the defining characteristic of production-grade AI.
